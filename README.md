## Описание архитектуры

### Домены и ответственность

- **Пользователи** — профили покупателей и продавцов;
- **Каталог** — товары, их карточки и поиск.
- **Персонализация** — подбор товаров с учётом истории заказов;
- **Заказы** — создание заказа и изменение его статуса.
- **Платежи** — сведения об оплатах, возвратах и комиссиях;
- **Уведомления** — информирование о статусах заказов.
- **Администрирование** — данные для модерации и обработки спорных ситуаций.

### Распределение доменов по сервисам

Модульный монолит: один backend-сервис содержит модули `User`, `Catalog`, `Personalization`, `Order`, `Payment`, `Notification` и `Administration`. Каждый модуль отвечает за свой домен.

Плюсы:
- Такое разбиение отделяет области ответственности в коде, но не требует отдельных процессов и сетевых вызовов между ними.
- Легче разработка (не надо настраивать сетевое взаимодействие)
- Легче перейти на микросервисы в будущем

Минусы:
- Меньше гибкости по сравнению с микросервисной архитектурой (нет возможности развивать модули независимо)

### Владение данными и взаимодействия

У backend одна физическая БД, поскольку это один сервис. Логически `User` владеет профилями, `Catalog` - товарами, `Order` - заказами и их статусами, `Payment` - записями об оплатах, возвратах и комиссиях, `Notification` - данными отправки уведомлений, `Administration` - решениями модерации. `Personalization` использует историю из `Order` и товары из `Catalog`. Модули обращаются к данным друг друга через внутренние интерфейсы, а не напрямую меняют чужие записи.

Все показанные взаимодействия синхронные: клиентские приложения вызывают backend по HTTP; внутри backend модули вызывают функции друг друга.

### Запуск сервиса

```sh
docker compose up --build -d
```

### Остановка сервиса

```sh
docker compose down
```

### Проверка health check

```sh
curl -i http://localhost:8080/health
```

Ожидаемый ответ: `HTTP/1.1 200 OK`, тело — `ok`.
